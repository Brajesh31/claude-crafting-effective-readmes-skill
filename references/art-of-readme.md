# README Design Principles

A README is a product interface for a repository. It should help a reader decide whether the project is relevant, understand what it does, and reach a successful first use.

## Reader-first structure

Write for the reader's immediate question:

1. What is this project?
2. Why should I use it?
3. Is it suitable for my situation?
4. How do I install and run it?
5. Where do I go when something fails?
6. How can I contribute or get help?

## Be specific

Avoid claims such as "powerful", "robust", or "easy to use" unless the README demonstrates them. Replace vague statements with concrete capabilities, supported environments, and a short example.

## Show the working path

A minimal, tested quickstart is usually more valuable than a long feature list. Include exact commands, expected output, and prerequisites. Separate the first successful run from advanced configuration.

## Keep promises aligned with reality

Do not advertise planned features as available. State version requirements, limitations, platform support, and known gaps. Add screenshots only when they clarify a workflow or result.

## Maintainability

- Keep the README close to the code and update it with behavior changes.
- Prefer short sections and descriptive headings.
- Link to detailed docs instead of duplicating them.
- Use tables only for genuinely tabular comparisons.
- Remove obsolete badges, broken links, placeholder text, and copied boilerplate.

## Quality test

Give the README to someone unfamiliar with the repository. Can they decide whether to use it and complete the quickstart without asking you questions? Fix the first point where they get stuck.
